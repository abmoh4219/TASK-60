# RailOps — System Design

## Overview

RailOps is a full-stack railway operations platform built with Rust.  It
provides a public passenger information kiosk, an internal operations console,
a staffing dispatch system, a credential management workflow, a content crawl
pipeline, and a configurable business rules engine.

All services start with a single command:

```
docker compose up --build
```

## Security

### Authentication
- Session tokens are random 32-byte strings generated by the backend.
- The SHA-256 fingerprint of the token is stored in the `sessions` table —
  the raw token is never persisted.
- Every authenticated request must include:
  - `Authorization: Bearer <token>` — raw session token
  - `X-RailOps-Ts: <unix_seconds>` — current UNIX timestamp
  - `X-RailOps-Sig: <hex>` — HMAC-SHA-256(`token`, `"METHOD\nPATH\nTS"`)
- The timestamp must be within ±120 seconds of server time (replay protection).
- Sessions expire after 30 minutes of inactivity; absolute expiry is 24 hours.

### RBAC

| Role         | Permissions                                                |
|--------------|------------------------------------------------------------|
| `admin`      | All permissions including rules config and user management |
| `ops_agent`  | Schedules, inventory, orders, passengers                   |
| `cs_agent`   | View orders, process refunds, cancel orders                |
| `dispatcher` | Staffing: shifts, contractors, assignments                 |
| `kiosk`      | Read-only public content (via unauthenticated kiosk API)   |

Permissions are enforced server-side via Actix extractors:
`RequireAdmin`, `RequireViewOrders`, `RequireManageOrders`, etc.

### PII Protection
- Passenger PII (name, email, phone) is AES-256-GCM encrypted at rest.
- Encryption key is derived from `SESSION_SECRET` via SHA-256.
- Only the last-4 digits of phone numbers are returned in list views (masked).
- PII purge is tracked via audit log; the actual wipe runs on explicit request.

### Audit Trail
- `audit_logs` table is insert-only (DB triggers block UPDATE/DELETE).
- All mutating operations write an audit entry with actor, action, detail, IP.
- Retention: 7 years (configurable via business rule).

## Crawl Pipeline

```
Source file (JSON) → RawItem → transform() → TransformedItem → QualityScorer
                                                                      │
                                           score ≥ 85? ──────────────┤
                                                Yes ─────► ingest to content_pages
                                                No  ─────► quarantine in quality_logs
```

**Transformation steps:**
1. `strip_html` — state-machine tag removal
2. `normalize` — collapse whitespace
3. `trim` — strip leading/trailing space
4. `abbreviate` — expand railway abbreviations (`stn.` → `station`, etc.)
5. `fingerprint` — SHA-256 of `title‖body‖source_url` for dedup
6. `slugify` — URL-safe slug, max 120 chars

**Quality scoring:**
- Completeness 50% (6 required fields)
- Accuracy 30% (body/title length, valid URL scheme)
- Timeliness 20% (age-based decay)
- Near-duplicate detection via `pg_trgm` similarity ≥ 0.92 → quarantine

## Business Rules Engine

All refund thresholds, hold TTL, and processing fees are stored as typed
key/value rows in `business_rules`.  The `RulesEngine` struct is constructed
per-request, queries the DB, and falls back to the constants in
`shared::rules` if a key is missing.

Key rule keys:

| Key                             | Default   | Description                        |
|---------------------------------|-----------|------------------------------------|
| `refund.full_minus_fee_hours`   | 24        | Full-refund window (hours)         |
| `refund.partial_hours`          | 2         | Partial-refund floor (hours)       |
| `refund.processing_fee_usd`     | 5.00      | Processing fee deducted from refund|
| `refund.partial_pct`            | 50        | % returned in partial window       |
| `hold.ttl_minutes`              | 15        | Order hold expiry                  |

## Data Flow: Order Lifecycle

```
POST /ops/orders  ──► pending
POST /orders/{id}/hold ──► held  (expires after hold.ttl_minutes)
POST /orders/{id}/confirm ──► confirmed
POST /orders/{id}/cancel  ──► cancelled
POST /orders/{id}/refund  ──► refunded  (RulesEngine evaluates max_amount)
POST /orders/{id}/rebook  ──► rebooked  (creates new order, links both)
```

Every state transition appends an `OrderEvent` and writes an audit log entry.

### Background Jobs

Two background tasks run alongside the web server:

- **Hold expiry** (30 s tick): cancels held orders whose `hold_expires_at` has
  passed.  Each expiry produces an `order_event` and an audit log entry.
- **PII purge** (5 min tick): purges encrypted PII for passengers who requested
  deletion and whose most recent trip completed > 30 days ago.

## Configuration

All configuration is provided via environment variables (see `docker-compose.yml`).
No `.env` file is required.

| Variable               | Description                                 |
|------------------------|---------------------------------------------|
| `SERVER_HOST/PORT`     | Bind address (default `0.0.0.0:8443`)       |
| `DB_HOST/PORT/NAME/USER/PASSWORD` | PostgreSQL connection details    |
| `SESSION_SECRET`       | 64-char secret for HMAC + PII key derivation|
| `ADMIN_SEED_PASSWORD`  | Used once on first boot to hash admin pw    |
| `TLS_CERT_PATH/KEY_PATH` | PEM paths (auto-generated if absent)      |
| `RUST_LOG`             | Log filter (default `backend=info`)         |

## Migrations

SQL migrations live in `migrations/`.  They are embedded at compile time via
`sqlx::migrate!("../migrations")` and applied automatically on startup.

`V1__initial_schema.sql` — full schema, seed routes/schedules/passengers/orders/content
`V2__extended_seed.sql` — extended seed data (crawl tasks, credentials, rules, etc.)
